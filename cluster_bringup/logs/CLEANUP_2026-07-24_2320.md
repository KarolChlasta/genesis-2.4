# Cluster cleanup — 2026-07-24 ~23:20

Killed on user request instead of waiting for the run-2 campaign's `timeout 4h`
(N=100000 was progressing too slowly to finish anyway, and the K=0/K=50000
subtraction methodology was already known-unreliable at N<=50000 — see

## What was killed
- `50_overnight_campaign.sh` + its `nxgenesis`/`nxgenesis_nocl` children on
  both inf03 and inf02 (the run-2 corrected campaign, mid-N=100000).
- **A genuinely orphaned process on inf03**: `nxgenesis_nocl -nosimrc -notty
  -batch Scripts/benchmark/hh1952_ap_verify.g 8 200` (PID 851165), running
  continuously since **2026-07-23** at ~99.8% CPU (over 24h of accumulated
  runtime). Root cause: an early exploratory test run tonight, from
  `genesis/src` (before the repo-root/`schedule.g` fix was known), invoked
  without an effective timeout and never terminated. It sat consuming a full
  CPU core on a **shared, no-queue** cluster node for over a day.
- A second stray process appeared moments after the first kill (PID 883153,
  same script, `nxgenesis` this time) and was also killed; both nodes were
  then confirmed clean (only standard user-session daemons remain: systemd
  --user, sd-pam, pulseaudio, dbus-daemon).

## Implication
The orphaned process was running throughout **both** the original 16h
campaign and tonight's corrected run-2 campaign, competing for a CPU core the
entire time. On a 128-thread (inf03) / 96-thread (inf02) node this alone
likely does not explain the K=0/K=50000 noise finding, but it is one more
reason not to trust fine-grained timing from either campaign without a rerun
on a verified-clean node.

## Action item for any future cluster session
Always verify `ps aux | grep kchlasta` is clean **before** trusting timing
data, and prefer wrapping every exploratory GENESIS invocation in `timeout`
(even quick manual tests), including ones run interactively for debugging.
